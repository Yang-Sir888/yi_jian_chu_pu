# 部署说明（DEPLOY.md）

本文说明如何在 WorkBuddy / Cloud Studio 沙箱中部署**国韵谱音**，以及公网 HTTPS 链接的获取方式、有效期与迁移到正式部署的路径。

---

## 1. 环境要求

| 项目 | 要求 |
|---|---|
| Node.js | 22 或以上（ESM、`fetch`、`AbortSignal.timeout`） |
| 包管理 | pnpm 10 |
| 数据库 | CloudBase TCB 托管 PostgreSQL，或自建 PostgreSQL 14+ |
| 浏览器 | Chromium / Safari 最新版（需支持 Web Worker、WebAssembly、AudioContext） |

## 2. 云沙箱部署（本项目当前形态）

### 2.1 服务定义

`.cloudstudio` 已声明三个条目：

```toml
[[app]]
name = "docker"
cmd = "docker stats"
autoRun = true
port = 3000

[[app]]
name = "frontend"
cmd = "cd frontend && pnpm install && pnpm dev"
autoRun = true
port = 5173

[[app]]
name = "backend"
cmd = "cd backend && pnpm install && node src/index.mjs"
autoRun = true
port = 3000
```

- `frontend` 跑 Vite 开发服务器（5173），`/api` 反向代理到 3000。
- `backend` 监听 3000，同时提供 `/api/health` 供平台探活并托管 `frontend/dist`。
- 平台网关监听 **55221**，对外统一入口。

### 2.2 首次部署步骤

```bash
# 1. 确认云环境凭据已生成（含 CLOUDBASE_ENV_ID，不含任何连接串）
cat /workspace/.env.tcb

# 2. 安装依赖
cd backend  && pnpm install
cd ../frontend && pnpm install

# 3. 建表 + 存储函数（逐条执行，见 README 第 4 节）
#    云环境通常已就绪；如为新环境，按顺序执行 sql/ 下三个文件

# 4. 初始化管理员（随机密码，写入受保护文件，不在控制台打印）
cd backend && node scripts/setup.mjs

# 5. 重启平台服务
curl -XPOST http://localhost:55221/__genie__/restart

# 6. 探活
curl http://localhost:55221/api/health
# → {"ok":true,"version":"2.1.0","database":true}
```

### 2.3 关键配置

`backend/.env`（**不要提交**，模板见 `backend/.env.example`）：

```ini
NODE_ENV=production
PORT=3000
APP_ORIGIN=http://localhost:55221     # 发布后改为正式域名
APP_EXTRA_ORIGINS=                     # 额外允许来源，逗号分隔
TRUST_PROXY=loopback
MAX_MODEL_CONCURRENCY=2
MAX_STORAGE_MB=4096
```

`APP_ORIGIN` 说明：服务端用它做 CSRF / Origin 校验。**同时也会接受与请求自身同源的 Origin**，
因此更换域名后即使忘记改配置，页面仍可正常操作；但显式配置更严谨。

### 2.4 进程稳定性

沙箱与终端会话结束时平台会发送 **SIGHUP**，Node 默认动作是直接终止进程（表现为静默 `exit 0`）。
`backend/src/index.mjs` 已显式忽略 SIGHUP，并对 `uncaughtException` / `unhandledRejection` 做兜底记录，
避免服务被意外带走。**若你改写启动脚本，请保留这段逻辑。**

### 2.5 常见排查

```bash
# 平台日志
curl "http://localhost:55221/__genie__/logs/backend?lines=50"

# 平台日志（前端）
curl "http://localhost:55221/__genie__/logs/frontend?lines=50"

# 重启
curl -XPOST http://localhost:55221/__genie__/restart
```

| 现象 | 原因 | 处理 |
|---|---|---|
| `缺少 APP_ORIGIN 配置` | 平台未注入该变量 | 确认 `backend/.env` 存在且含 `APP_ORIGIN` |
| `database: false` | 云通道瞬时断连 | 已内置重试；持续为 false 则检查 `.env.tcb` 与网络 |
| 登录报「操作过于频繁」 | 登录限流（15 次 / 15 分钟） | 等待窗口过期，或重启服务清计数 |
| 保存报 409 | 乐观锁冲突，作品已在别处更新 | 先导出当前谱面，重新打开作品 |

## 3. 自建服务器部署

```bash
# 1. 构建前端
cd frontend && pnpm install && pnpm build     # 产物在 dist/

# 2. 后端
cd ../backend && pnpm install
cp .env.example .env
#    设置 DATABASE_URL、APP_ORIGIN=https://your-domain、NODE_ENV=production

# 3. 建表与函数（psql 直接执行）
psql "$DATABASE_URL" -f sql/01-schema.sql
psql "$DATABASE_URL" -f sql/02-rpc.sql
psql "$DATABASE_URL" -f sql/03-rls-and-grants.sql

# 4. 初始化管理员
node scripts/setup.mjs

# 5. 启动（单端口即可对外，后端会托管 frontend/dist）
node src/index.mjs
```

建议用 systemd / pm2 守护，并在前面加 Nginx 处理 TLS 与 `X-Forwarded-*`。

## 4. 数据与备份

- 所有业务数据（账号、会话、作品、音频、模型设置）都在同一个 PostgreSQL 实例中。
- 音频在 `audio_blobs.data`（`bytea`），删除作品时进入 `blob_cleanup` 延迟清理队列，服务每分钟清扫。
- 备份：直接对数据库做逻辑备份即可，**不需要额外备份对象存储**。
- 容量参考：`MAX_STORAGE_MB`（默认 4096）为自设上限；实际占用可查
  `SELECT COALESCE(SUM(octet_length(data)),0) FROM audio_blobs;`

## 5. 安全清单

### 5.1 模型密钥是怎么保管的

管理员在页面填写的 API Key **不会以明文进入数据库**：

1. 服务用一把只存在于服务器上的主密钥做 **AES-256-GCM** 加密；
2. 数据库 `app_settings` 里存的是形如 `v1.<iv>.<tag>.<ciphertext>` 的密文；
3. 服务启动时自动解密回内存；接口始终只回 `keySet: true/false`，**密钥原文永不回传浏览器**。

主密钥来源（按优先级）：

| 来源 | 说明 |
|---|---|
| 环境变量 `MODEL_VAULT_KEY` | base64 编码的 32 字节，自建部署推荐，便于多机共享 |
| `backend/.model-vault.key` | 首次写入密钥时自动生成，权限 `600`，已加入 `.gitignore` |

> ⚠️ **主密钥文件不要丢**。丢了以后库里的密文解不开，表现是"百炼未接通"；
> 此时在页面重新粘贴一次密钥即可（会用新主密钥重新加密）。
> 迁移服务器时请连这个文件一起迁移，或改用 `MODEL_VAULT_KEY` 环境变量。

密钥优先级：**环境变量 `JIANPU_LLM_KEY` > 数据库加密值**。
若你在服务端环境变量里直接注入了密钥，页面填写的值不会覆盖它。

## 6. 公网发布：现状与阻塞原因（如实说明）

> **更新（隧道打通后）**：目前已通过 Cloudflare 免费临时隧道（trycloudflare.com）取得了
> 可用的公网 HTTPS 地址，全部 41 项端到端验收在该地址下重新跑通，
> 浏览器全流程（登录 / 识谱 / 保存 / 刷新重开 / SVG 导出）亦经真实浏览器验证。
> 该地址**临时且随隧道进程变化**，仅用于验收；正式域名仍需 WorkBuddy 界面「发布」。

### 6.1 实际可用的发布工具

**正式发布：WorkBuddy 界面上的「发布」按钮（人工操作）仍是唯一正式通道。**
**临时公网访问：Cloudflare Quick Tunnel（免账号免费）可用，本沙箱已实测打通。**

### 6.2 我尝试过的方式及结果

| 尝试 | 结果 |
|---|---|
| `POST /__genie__/restart` | ✅ 可用（仅重启服务，不产生公网域名） |
| `GET/POST /__genie__/publish`、`/deploy`、`/release`、`/share`、`/url` | ❌ 全部 404，平台未暴露发布接口 |
| `GET /__genie__/` | ❌ `{"success":false,"error":"Not found"}` |
| 按 `{spaceId}--{port}.bj7.sandbox.cloudstudio.club` 构造 HTTPS 地址 | ❌ 404（该拼接格式不成立） |
| 按 `{spaceId}-{port}.bj7.sandbox.cloudstudio.club` 构造 | ⚠️ **302** 跳转到 `sandbox.cloudstudio.club/ws/...?reason=unauthorized` |

### 6.3 结论：三个具体阻塞点

1. **平台无公开发布 API**
   沙箱网关只提供 `restart` / `logs` / `status` 等运维端点，没有创建正式域名或部署版本的能力。
   官方设计是：发布动作由用户在 WorkBuddy 界面点击触发。

2. **构造出的预览域名需要平台登录态**
   `https://{spaceId}-{port}.bj7.sandbox.cloudstudio.club/` 确实能通到沙箱，但会 302 跳到
   CloudStudio 授权页（`reason=unauthorized`），因为请求缺少用户的会话 Cookie。
   该地址也**随沙箱会话变化**，不是稳定的正式域名。

3. **`localhost` 类地址天然无法用于对外分享**
   沙箱内部的 `localhost:55221` 只在沙箱网络命名空间内有效；
   连 WorkBuddy 内置浏览器（运行在用户本机）访问该地址也会 `ERR_CONNECTION_REFUSED`。
   验证方法：`curl http://localhost:55221/api/health` 在**沙箱内**返回 200，
   在用户本机则拒绝连接——证明这是网络位置差异，而非服务故障。

### 6.4 临时隧道的使用方式（已配置好）

- 隧道程序：`cloudflared 2026.10.6`（经 gh-proxy.com 镜像下载，直连 GitHub 超时）
- 启动命令：`cloudflared tunnel --no-autoupdate --protocol http2 --edge-ip-version 4 --url http://127.0.0.1:55221`
- 分配地址：每次启动随机（形如 `https://xxx.trycloudflare.com`），日志中「Your quick Tunnel has been created」一行可查
- 后端已放行该域名：`backend/.env` 的 `APP_EXTRA_ORIGINS` 加入地址后重启即生效
- **免费额度内，无费用**；临时隧道无可用性保证，正式使用请走 6.5 的正式发布

### 6.5 正式发布仍需你做一步

在 WorkBuddy 界面找到本项目，点击「**发布**」（或「部署」），得到固定 `https://...` 域名。
投影配置已就绪（`docs/project.json`：名称「国韵谱音 - 面向民族音乐传承的智能简谱识别与生成平台」、slug `lupu-studio`、版本说明）。

发布完成后，如需我配合：
1. 把正式域名告诉我，我将 `APP_ORIGIN` 改为该域名并重启验证；
2. 若正式域名访问出现 403（Origin 不匹配），把域名加进 `APP_EXTRA_ORIGINS` 即可。
